# Agent-native 经营协同蓝图｜从文章中提炼的长期方法
- 日期：2026-10-11
- 状态：**参考文章提炼 / PROPOSED（尚未批准建设中台）**
- 来源：Owner 提供的一篇关于小公司基于飞书、AI Agent、MCP、应用/Skill广场和权限系统打造内部中台的文章。其部署速度、效果和安全性是作者自述，本项目不作为已验证事实。
- 当前主线：灵生10台试采准备；不因本文改变13号现场学习或正式合同/现金流门禁。

## 一句话
先把真实的场景、人员、任务、质检、结算的数据和负责人做成连续协作闭环；达到规模之后，再把高频流程做成Agent可调用的轻量应用。**不从租服务器、MCP中台或设计系统开始**。

## 文中可借鉴的核心
1. **共享真实数据源而不是到处复制表**：场景、员工、任务、验收和结算以清晰的权威表维护；AI做读取、草拟、汇总、异常提示。
2. **把重复动作变成可复用工具**：表单、报价计算、场景准入审查、试采日报、任务提醒、开票申请等。
3. **Skill标准化**：把“怎么询问场景老板、怎么审核有效小时、怎么培训新人、怎么写日报”等变成版本化SOP。
4. **权限分层和审批**：场景联系人、人员资料、合同价格、财务账款按角色访问；付款、批量发送、签约等外部动作有人审核。
5. **统一入口和可发现性**：员工不必学习一堆软件，日常从简单手机页面/表单进入。
6. **异常驱动改进**：每次返工和表单错误都能回到SOP/系统规则中修正。

## 当前项目已具备
- GitHub Knowledge Harness：长期原则、项目状态、上游、证据和经营假设
- WHAT日计划、周报、行业雷达的运行规则
- 场景/人员/合同/试采的模板

## 最大缺口
GitHub知识库负责经营决策、方法和非敏感摘要，但**不是天然的实时业务数据库，也不能自动从私人微信同步联系人、授权和结算数据**。现阶段尚未形成：
- 经授权的结构化场景联系人/跟进台账
- 任务派发→采集→审核→返工→结算的状态闭环
- 明确的角色/权限和隐私留存规则
- 数据输入、复核、变更记录和数据质量验证

## 建议分三阶段（非当前承诺）
### A｜0-10台：最小协同系统（马上够用）
工具优先级：已有表格/聊天 + GitHub知识库。若要多个人共用，选择支持角色授权的表格/协作工具，不强制采用飞书。
- 结构化数据表：
  - 场景台账：内部ID、经营类别、区域、地址、联系人/电话（只在受控业务系统）、可执行动作、授权状态、下一次跟进、费用/风险。
  - 人员台账：内部ID、成年确认、培训、出勤、操作技能、通过率、可排班状态（个人敏感资料限授权人员）。
  - 任务/设备日报：上游任务ID、场景ID、设备ID、原始小时、提交小时、验收有效小时、返工原因。
  - 财务台账：押金、租金、工资、场景成本、已验收收入、开票/应收/到账、结算日期。
- 统一流程：现场截图/口述→人工确认关键信息→结构化入账→自动/半自动汇总→负责人核查异常→更新经营决策摘要。
- 第一批SOP：场景接洽、场景授权/隐私、采集员入职培训、数据质检、当日盘点。
- 适用范围：只为第一轮真实试采服务。

### B｜10-20台稳定、真实回款后：轻量业务工具
在高频痛点经过连续验证后再做：
- 手机端场景录入/跟进提醒
- 采集员签到/任务完成与质检异常单
- 设备领还记录
- 自动生成老板日报/周报和现金流预警
- 保留审批记录、数据变更轨迹与权限分层

### C｜多场景、30-50台、多上游成熟之后：Agent-native运营中台
只有当员工数量和流程复杂度证明值得建设，才评估：
- 内部应用入口 / 应用目录、Skills目录、版本管理
- 公司身份登录、权限、操作审计
- API/MCP等标准化Agent接入
- 数据看板、多租户/多合作方任务隔离
- 独立服务器或托管部署、备份与恢复

## AI可做、必须由人做
- AI适合：初步抽取、识别缺失字段、生成话术、统计、草拟、推荐跟进、异常预警。
- 必须人工：场地方授权、员工录用、合同签章、押金/付款、接受上游结算争议结论、系统权限授权。
- **禁止以聊天内容自动确认合同有效、场景已授权、数据已到账。**

## 什么时候升级工具
- 同一字段经常重复录入，或每周持续发生人工错误；
- 多名员工同时更新导致混乱；
- 一天采集数据必须反复由不同人转述；
- 异常未被追踪，审核结果与账款对应不上；
- 人员个人数据或合同数据需要正式权限隔离。
满足真实痛点才考虑开发专用应用，并先做小应用原型；不要先做企业中台。

## 接下来一周最重要的落地动作
1. 13号培训前，准备可使用的场景/人员清单和试采日报字段。
2. 向灵生确认是否提供租户后台、任务/审核导出数据和管理员权限（这可能替代我们自建系统的大部分需求）。
3. 试采开始后只记录最关键的原始小时、有效小时、返工、设备/场景、人工、租金、回款节点。
4. 首轮复盘再决定到底需要哪些业务工具；不要提前建设复杂平台。

## 事实边界
文章里的飞书实时双向同步、Agent自主部署、MCP权限、应用广场等效果是作者场景的描述；复制到本项目需要额外的账号授权、接口、技术验证、权限和合规设计，不是GitHub现有能力。

## 1. Owner当前考虑的资源调配
- Owner有Linux服务器，记忆中该服务器可能仍运行一个以前用于**校外托管业务**的智能体；具体进程、是否仍运行、是否有业务依赖和资源占用**均未经核验**。
- 优先查服务器是否能**同时运行原托管Agent与唯一Hermes**；若两者资源足够且权限/端口/工作目录/数据目录/调度分离，则可共存，不必为迁移而删除前者。
- 如果资源不足或Owner决定暂停旧托管业务，Owner希望能够将旧智能体相关内容**完整备份，以后可恢复**，并在可恢复前提下清理旧运行环境，优先让服务器只运行Hermes。
- **“Hermes唯一数字员工”宪章指公司数采运营的一个正式Hermes身份**，并不等于Linux服务器技术上只能有一个不同业务的Agent；两个不同业务智能体共存可行性由实际资源和隔离决定。
- 不要擅自将服务器上的托管Agent视为Hermes旧身份，更不允许把二者记忆或凭据混合。

## 2. Codex第一阶段只读检查（不得改动现有服务）
- 服务器：Linux发行版、CPU核数、内存、swap、磁盘可用空间、实时和日常峰值资源、网络带宽及安全更新状况。
- 进程与工作负载：systemd、Docker/compose、容器、计划任务、监听端口、反向代理、服务自动启动、挂载卷、数据目录、日志、依赖；明确哪些属于托管Agent，是否正在对外提供服务，是否含未完成定时任务。
- 托管Agent资产：源码/版本、身份配置、可脱敏的Skills和业务知识、数据库与WAL、会话、向量索引、上传文件、模型配置、定时任务、外部集成、数据库/容器卷以及恢复依赖。只报告路径/类型/规模，不读取/外传凭据内容。
- Windows上Hermes真实安装状态还要单独核对：原本机2026-10-15审计为Windows 11、Hermes CLI/agent 0.20.4、桌面版，活动数据根 `<USER_HOME>/.hermes`，另有 `<LOCALAPPDATA>/hermes`，存在SQLite/WAL、浏览器/CDP/Windows专属依赖；旧审计不是当前状态。
- 评估可否两个agent通过不同用户、服务、端口、数据库、权限及调度独立运行；估算峰值资源和运维风险。运行状态与资源不足不能未经实测便声称确定。

## 3. 备份位置：GitHub与完整归档要分开
- **GitHub仓库**保存脱敏源代码（合法可归档部分）、Skills定义、配置模板（全部secret置为占位符）、部署清单、版本、依赖锁文件、恢复操作说明、校验摘要/备份清单和不含私人数据的迁移决策史。
- **不要把完整生产环境直接打包推入GitHub**，哪怕私人仓库：可能含密码/Token/Cookie/私钥、客户/学生个人信息、聊天和工资数据、数据库以及体积过大的文件。GitHub历史版本留存和仓库成员权限使撤销/彻底抹除秘密困难。
- 全量可恢复备份如确有需要，应在Owner批准后保存在**Owner控制的加密备份存储**（例如私有加密存储或有访问控制的备份盘），仓库只记录文件清单、非敏感恢复定位信息与验证结果；加密密钥独立保存，切勿与密文同库提交。
- 备份包括服务配置、容器卷、数据库一致性快照、计划任务、身份记忆、Skills及恢复所需版本与环境信息；SQLite不能在活跃写入时只复制主DB忽略WAL。
- 恢复演练是清理的先决条件：校验备份、沙盒恢复并以虚拟数据验证可启动、能力/定时任务可恢复且不会触发正式外发。

## 4. 决策门槛与执行顺序
1. **只读盘点**现有服务、资源、风险，交付去敏报告与建议；本阶段不安装/不删除/不停服。
2. 如果足够共存，则建议保留旧业务Agent（或按Owner后续要求暂停调度）与Hermes分离运行，避免同时启动两个**Hermes**生产实例。
3. 如果资源紧张且需释放，先给Owner列出具体停用/备份/清理对象、业务影响、存储地点、恢复步骤和费用；取得明确批准后操作。
4. 先做可验证、可恢复的全量加密备份和恢复演练，再安排维护窗口停用旧服务，检查对业务的实际影响；**永久删除必须再次有明确范围许可**，保留回退窗口。

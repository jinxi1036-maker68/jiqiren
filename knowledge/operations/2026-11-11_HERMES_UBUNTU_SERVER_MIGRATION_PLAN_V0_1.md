# Hermes 唯一正式数字员工：Windows → Ubuntu 服务器迁移可行性与分阶段计划 V0.1

**日期**：2026-11-11
**来源**：Owner明确报告现有一台 Ubuntu Linux 服务器，**2 vCPU、4GB RAM**；希望把个人电脑现有唯一 Hermes 数字员工部署到服务器以长期持续工作。
**当前状态**：PROPOSED / FEASIBILITY_ONLY；**没有实际登录服务器、没有进行安装、没有复制任何本机私人数据、没有停用旧电脑任务、没有完成切换**。
**约束**：以 `knowledge/HERMES_DIGITAL_EMPLOYEE_CHARTER.md` 为唯一岗位理念权威。不是创建第二名正式员工；服务器只是同一 Hermes 的新承载位置。不得在未批准下清理现有个人电脑的数据或全量复制凭据。

## 目标与技术判断

- Ubuntu 2核4GB可以优先承载**调用云端模型API**的轻量 Hermes CLI/gateway、消息收发、少量定时任务、基本文档操作。**不能按这份内存预算承诺本地运行大型语言模型**。
- 官方 Docker 资源说明（查阅于2026-11-11）：最低1核/1GB，建议2核/2～4GB；浏览器自动化是最耗内存功能。实际资源消耗取决于并发、工具、日志、其他已安装进程。官方文档： https://hermes-agent.nousresearch.com/docs/user-guide/docker
- 需要再核实服务器磁盘可用空间、swap、网络访问、系统架构、防火墙、现有容器/其他服务；额外建议至少留出数GB安全余量，不将官方最低磁盘值当作老Hermes完整历史迁移的足够空间。
- 官方有 Ubuntu/Linux CLI安装路径和 Docker Gateway 路线：https://hermes-agent.nousresearch.com/docs/getting-started/installation
- 官方 Feishu 通道支持`websocket`（推荐），由 Hermes 出站连接飞书、不用公开 webhook 入站端口：https://hermes-agent.nousresearch.com/docs/user-guide/messaging/feishu
- 如要保留个人电脑上的Hermes Desktop可视化界面，官方支持让Desktop连接远端已运行的后端，但要按当前版本的远程连接文档与身份认证配置，**桌面客户端是操控同一服务而不是额外启动第二名员工**：https://hermes-agent.nousresearch.com/docs/user-guide/desktop

## 已知本机基线与特殊迁移风险

来源：`hermes/reports/PHASE_01_LOCAL_AUDIT_REPORT.md`（2026-10-15历史快照，必须重新核验）
- 源端是Windows 11，桌面+CLI+后端；当时 Agent/CLI版本为0.20.4，活动用户数据根为 `<USER_HOME>/.hermes`，另有 `<LOCALAPPDATA>/hermes` 备用数据根，**不能选错**。
- 当时SQLite `state.db` 基础文件约**1.213GB**，有WAL；会话多。迁移不能仅复制主.db，必须一致性备份并做完整性验证。该历史值不是2026-11-11实时大小。
- 旧Windows特定GUI、浏览器已有登录态、旧脚本MCP、密钥加密和本地文件路径，可能不能跨Linux直接复用。相关工具应逐项替换/重新授权。
- 先核对最新版原本机状态及远端支持的版本与schema，再决定如何处理版本差异。**不要把旧0.20.4全量HERMES_HOME未经验证直接丢给最新生产容器。**

## 分阶段步骤和验收

### 阶段0：只读核实（尚未执行）
- 服务器：`lsb_release -a`, `uname -m`, `free -h`, `df -h`, `docker --version`；确认磁盘余额、swap和运行其他服务；**只提交非敏感配置，不提交IP/密钥**。
- Windows：在原Hermes可访问的环境只读核对实际版本、活动`HERMES_HOME`、数据库大小/WAL、Skills/MCP、Feishu连接方式、已启用定时任务、Windows桌面自动化依赖。与2026-10-15审计差异形成新清单。
- Owner确认迁移目标：迁移长期记忆/已需Skills/工作清单/有效定时任务，哪些历史会话及旧业务凭据需继续保存；优先最小必要数据。

### 阶段1：受控远端运行环境（未执行）
- 新建受限Linux服务用户或经审核的Docker持久化卷；初期用官方经过核对的**指定稳定版本**，不要盲目`latest`覆盖旧数据。
- 先仅连云端模型API，运行正常对话、文件/日志写入与重启恢复测试，不接真实飞书token、不启旧cron、不登录真实客户后台。
- 资源初始以单实例、单并发浏览器为上限；观测实际使用，必要时设置合理swap和告警，保留操作系统内存余量。

### 阶段2：迁移本机唯一身份与权限（需要单独Owner明确授权）
- 选定停写窗口；本机经过一致性备份，含`SOUL.md`、`memories/`、经挑选的`sessions/`、`skills/`、实际启用调度、相关数据库及WAL/SHM、岗位配置和授权状态清单（不是把秘密上传GitHub）。
- 加密传输至私有服务器，检查备份校验/DB完整性；应用兼容迁移；跨系统不兼容的Windows浏览器登录态/密钥重新登录授权，不解密绕过保护。
- 在服务器验证“仍然是同一岗位、同一份已确认记忆/规则、同一批工作待办”，且不重复发送飞书消息。服务器试运行不接生产写操作。

### 阶段3：逐项能力验收与唯一运行切换（未执行）
- 飞书：按官方支持的WebSocket模式进行新服务器配对、授权用户限制、单通道送达测试；服务器正式上线之前停止电脑旧网关连接，避免一条消息被重复处理。
- 定时：先测试合成任务、守护重启、去重、跨日恢复；切换时停旧cron再启新cron，避免双份派单/发送/账务行为。
- 浏览器：验证无头Chrome/Playwright与实际授权页面的只读连接，Windows桌面级依赖以独立兼容方案处理；对验证码/二次认证保持人工授权，不假定浏览器cookies可复用。
- 在Owner验收后将**Ubuntu服务器**定为唯一正式执行端；原Windows暂仅作受控恢复点/本地客户端，不继续承担同一生产任务。并按既定存留期限处理副本，不长期运行双员工。
- 验证断网重连、服务器重启、API失效、飞书掉线、浏览器内存峰值、备份恢复；异常时关闭服务器网关并按回退步骤恢复原电脑。

## 第一轮建议

先采集5项不敏感服务器只读信息：系统版本、CPU架构、内存、磁盘空间、Docker有无；并同步只读检查原本机Hermes版本/数据根/旧定时任务。准备信息之前**不执行安装、复制密钥或数据迁移**。

如果未来小U每60秒处理视觉截帧，应将其作为**单独预算/隔离的视觉推理服务**考虑：本机2核4GB优先承载Hermes协调与消息，不承诺它同时承载多设备持续视频模型推理。

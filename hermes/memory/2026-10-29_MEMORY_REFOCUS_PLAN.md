# 原Hermes长期记忆整理草案

状态：**准备完成、未部署**。2026-10-29，Issue #9 / Draft PR #20。Owner指出记忆混杂并要求继续下一步；本轮整理可审查草案，不改原记忆、身份或服务。公司最高岗位宪章保持原样。

## 1. 问题与证据边界

Owner提供的Hermes回复把历史业务、个人背景、旧技术环境及刚发生的业务观察并列称作长期记忆。**该回复是Hermes自述，不是原文件逐项导出**；不能据此认定所有条目都在MEMORY.md，也不能认定它已把最新设备数据写入长期存储。

本轮仅检查原安装的公开程序源码、当前记忆配置白名单和原文件大小/SHA256，不读取私人记忆正文、完整系统提示或会话数据库。当前两份文件合计25,429字节；配置memory_enabled与user_profile_enabled均true，字符上限分别10,000/5,000，外部provider字段为空。文件大小不是内存占用，也不能据此量化模型变慢或错误的原因。

**源码已证实**：原H下的`memories/MEMORY.md`与`memories/USER.md`被内置MemoryStore精确读取，按`\n§\n`分条，在load_from_disk时形成冻结快照；启用后由system_prompt.py加入上下文。中途改磁盘不保证正在运行的Agent或既有对话立即换记忆。gateway/run.py还缓存会话Agent，历史消息和持久提示也可能继续携带旧背景。因此“文件已改”“新快照已装载”“旧会话不再影响回答”须分别证明。

定位依据见随附JSON：memory_tool.py的get_memory_dir/load_from_disk/_parse_entries，agent_init.py的持久记忆初始化，system_prompt.py的memory块装配及gateway/run.py的会话Agent缓存。没有调用MemoryStore加载私人正文、没有启动Hermes或模型。

## 3. 拟实施的最小范围（本轮未执行）

1. 确认Owner批准两份草案及旧业务退出默认加载；在本机私有范围完成原条目归类，发现未覆盖且有价值的现岗位条目就补充草案供核对，不无条件整份覆盖。只针对两份记忆操作，不扩到Skills、cron或原资料删除。
2. 实施时重新核对两份原SHA及保护清单其余57项、运行空闲和路径。仅为两份原记忆及本次确要改变的自有保护元数据保存必要私有前像；沿用已验证的`.lingju-hermes-recovery`根目录，实际建子目录时再次验证路径和私有ACL。拟恢复保留期14天供Owner决定，不自动删除，不把恢复副本永久当第二名员工记忆库。
3. 经确认后，仅写`H/memories/MEMORY.md`、`H/memories/USER.md`。使用原生分条格式、UTF-8与LF；最终序列化为ENTRY_DELIMITER.join(entries)，不增加尾部空条目。按两份候选各自payload SHA核对，保持memory开关和字符上限不变。
4. **同时处理原有浏览器保护依赖**：当前飞书入口会检查含两份记忆在内的59项保护基线。仅改记忆而沿用旧哈希会被判为越界修改。拟创建一份派生基线，明确只更新这两个批准目标的预期哈希，其余57项逐项保持原值、原基线留作依据；更新自有gate中的基线SHA和本次启动的基线路径，不重建或无条件接受整个现状。不修改原config/MCP登记。
5. 拟获准后在原网关空闲时正常重载一次，让新基线路径和新记忆进入原进程；飞书等通道短暂重连。若仍沿用旧对话缓存，先记录阻断；后续由Owner通过原入口建立正常新工作上下文，不删旧会话、不改数据库或完整system prompt，不自动发送模型消息。本轮没有预先取得这次新增重载授权。
6. 只读核对正式文件payload、两项新预期与其余57保护、原H/W/身份、已验证Ego工具及通道状态。源码/静态检查与实际模型加载分别记录；是否需要一次正常工作对话，由Owner决定，不能自动用模型测试替代证据。

原MEMORY/USER写入属于此前受保护范围。本轮“继续”用于准备上述具体草案；**实际替换两份记忆、必要保护元数据调整及一次空闲重载，仍须Owner明确批准这份具体范围**。依据为Owner此前“不修改旧记忆”的边界与仓库AGENTS.md“对于……记忆重置……先确认具体范围”。不是岗位宪章禁止整理；宪章支持合理整理。

**另一个已发现的实际限制**：当前只读带教保护会冻结两份记忆的哈希，因此未来Hermes若自主写长期记忆，也会触发这套保护；当前飞书工具范围也不能据此推定具有memory写工具。一次性整理与后续自主长期学习是两回事。本方案只处理经批准的整理，不放开memory工具、不关闭保护、不宣称已经具备自主持久记忆能力。后续如要允许员工自己沉淀经验，应单独明确工作笔记与身份/凭据保护的边界，不能长期用人工改基线代替员工成长。

## 4. 恢复和停止条件

- 任一原哈希、路径、权限或保护项与批准前置不同，停止；先确认新增内容，不能一键接受当前基线。
- 恢复仅针对本轮写入且当前仍匹配本轮输出哈希的单文件；不整份恢复H/W。存在并发写入时停止，不能覆盖Hermes或Owner新记忆。
- 跨两份文件的更新不视作文件系统整体原子事务；未完成时保持未就绪，按批准的条件化恢复规则恢复本轮已写且未再变化的文件，不能宣告部分部署成功。
- 保护基线/元数据恢复也需匹配本轮输出，恢复原记忆时同步恢复对应保护关系。禁止用“修复”名义关闭保护、删除会话或卸载工具。

## 5. 验收标准与本轮结果

- 草案：公司岗位与自主性完整；两份各低于当前字符上限；无旧业务角色/过时数字/凭据；原生分条格式、引用与payload SHA可复现。
- 后续本机部署：仅两份批准记忆及必要自有保护/启动元数据改变，其余文件不变；原H/W、同一身份、Ego与正常通道保留；前像可单文件恢复。
- 后续实际工作：依据收据分别确认记忆加载和任务表现；不以答案像模板推断自动加载，不要求固定思考或点击顺序。不承诺抹去全部历史上下文或永不再犯错。
- 本轮：只制作仓库草案和脱敏索引；原Hermes写入0、删除0、重载0、模型消息/请求0、浏览器/业务平台动作0。当前记忆未改变，因此不能说Hermes已完成记忆整理。

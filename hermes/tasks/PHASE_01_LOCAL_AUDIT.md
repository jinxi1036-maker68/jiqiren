- GitHub `jinxi1036-maker68/jiqiren`同时是现有 `knowledge/`业务知识库和新增 `hermes/`开发档案库，实行版本管理。
- 网页线索：`https://ldp.lingrobotics.com/statistics`（无需在本次主动尝试第三方登录）。
- Hermes 必须具备“已知待办持续跟进”意识：例如数据上传后1—2天审核才返回，若有更新应可发现并主动汇报；具体实现和频率以后研究。

## Codex执行顺序

### A. 仓库轻量背景读取
1. 读取 `knowledge/00_START_HERE.md`，按 `knowledge/KNOWLEDGE_HARNESS.json` 和 `knowledge/CURRENT_WORK.json`最小加载；不要对整个仓库全量扫描来揣测当前事实。
2. 阅读 `hermes/README.md` 和本任务文件；不要将已有 `knowledge/` 文件整体迁移到 `hermes/`。
3. 验证Git版本环境：当前本地代码目录、远端 origin、分支、未提交变更；**不要擅自覆盖或强推**。

### B. 本机只读盘点（需要用户授权的本地电脑环境）
1. 找到 Hermes 的真实安装方式、版本、目录、运行进程/启动命令（只记录不含秘密的描述）。
2. 盘点持久记忆、角色指令、历史会话、Skills、插件、工具、调度/定时任务、代理权限与现有脚本，分别说明**位置、作用、相关性、是否可禁用/归档**。
3. 检查现有浏览器控制工具：能否读取DOM/文字、导航网页、识别状态、点击/输入、截图、文件上传/下载、表格解析；仅在不触及灵生登录或个人数据的**本地/公开演示页面**做非破坏性测试；如果环境不支持相关能力，如实记录。
4. 梳理记忆装载逻辑：哪些内容自动进入Hermes上下文、哪些仅存储在磁盘、哪些属于工具配置；判断创建专职数采身份/工作区的可行方式。
5. 盘点敏感数据位置和Git忽略规则，**不得输出实际秘密内容**，仅报告“存在、风险、是否需隔离”。

### C. 提出清理与岗位训练方案（不执行）
1. 将每类记忆或工具划为：**保留/归档/停止自动加载/候选删除/需Owner判断**，并说明理由。
2. 设计先备份再优化的步骤和可恢复性检查。保留必要的浏览器配置、账号授权、操作历史与审计记录；未经批准不能永久删除。
3. 提出如何让Hermes学习灵生后台页面的方案：未来经Owner授权后，先绘制页面地图（导航、名称、用途、字段、按钮、输入输出、依赖权限、风险），用演示数据做只读验收。
4. 提出自主巡检的最小能力：记录前后两次待审/已审状态，发现新质检标注，把“后台事实/疑似原因/改进建议”分开，支持在无新数据时准确回复“尚无新增”。
5. 不决定最终日常巡检的固定时间、异常阈值、汇报形式；列成待与Owner协商的要素。

### D. GitHub交付
1. 形成脱敏的 `hermes/reports/PHASE_01_LOCAL_AUDIT_REPORT.md`，写明检查时间、OS环境、Hermes实际安装模式、现有能力、缺失项、浏览器非业务演示测试证据、改造建议和阻塞事项。
